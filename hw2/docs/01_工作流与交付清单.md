# 工作流：六块任务、两次主要提交

日期：2026-10-28。截止：2026-11-08结束前，建议23:59之前完成。

## 先校正两个理解

1. 预测必须在正式收数前写好并commit。第一次主要提交不是“代码而已”，而是可运行程序、设计说明、预测、分析规则的共同快照。预测应在设计时形成，预实验可以帮助排错和调整，但调整后要先更新并提交再收正式数据。
2. “全体研究报告”只是汇总本作业真实参与者结果的一份研究报告，不是另做第三个实验、另找一个全班大样本。全班数据对比是可选加分项。

## 六块工作

| 块                 | 要回答的问题                           | 本地交付物                                             | 完成门槛                                                                  |
| ------------------ | -------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------- |
| 1 文献与原范式     | 原研究怎么做、发现什么，我们保留什么？ | 文献出处、原方法卡、原结果参照、适配差异表             | 可由原文定位关键操作；不只凭摘要写程序                                    |
| 2 改进与研究设计   | 改哪个因素，为什么，预测什么？         | 两张设计卡、备选权衡、被试设计、试次表、预测和分析草案 | 每实验有改进；至少一项实测；学生理解并决定                                |
| 3 程序与收数前提交 | 能否可靠呈现、记录、上传？             | 前端、老师接口配置、CSV/JSON备份、README、验证记录     | 知情同意→编号→指导语→练习→正式→结果；每条件≥10；预测先commit              |
| 4 正式收数         | 有多少真实、完整、可用的他人数据？     | 平台记录、本地原始备份、参与完成/排除清单              | 每个实验≥5名他人；目标5名完整参与者，可按预定规则扩展至10名；调试数据分开 |
| 5 分析与简洁报告   | 是否出现经典效应，改进是否得到支持？   | 可复现分析、统一图表、网页研究报告、文字讨论           | 按被试计算效应；原文对比；不确定性和局限；不强行追求显著                  |
| 6 最终验收与提交   | 助教能否运行、核验和读懂？             | 最终GitHub版本、平台数据、README、报告与汇总           | clone运行、接口人数、版本、图文数字相符；密钥未泄露                       |

块1和2需要相互校正；程序试运行后若改了设计，必须更新预测版本。无需把每块机械地当成只能执行一次的阶段。

## 各阶段提交的实质

### A：收数前版本

- 完整前端源码和清楚的运行方法。
- 原论文及浏览器适配说明。
- 每个实验的条件、自变量、因变量、试次数、顺序平衡。
- 预先写明的效应、预测方向、有效数据规则、分析方法。
- 老师项目码、AI使用说明；没有下载密钥。
- commit并推送后记录SHA与正式收数开始时间。收数前再修改，可以有多个commit；两次主要提交不等于总共只能commit两次。

### B：收数后版本

- 保留A的预测和历史，不覆盖成“我们原本就这样想”。
- 增加实际样本/试次数、排除理由、结果图表、与原研究比较、讨论和局限。
- 分析脚本与适合公开的匿名汇总；逐试次原始记录在老师平台和本地备份中可核验。
- 网页中一份正式研究报告即可，同时分析两个实验。不另强制Word/PDF，也不强制实时榜单。

## 两个实验与被试内/间设计是不同层次的问题

- 同一网站不意味着每人必须完成两个实验。
- 分别招募两组人各做一个实验可行；每个实验仍须≥5名他人，若目标每实验10人则需约20名不同参与者。
- 在同一实验中，原版/改进分给不同人是被试间设计；同一个人做两者是被试内设计。
- 当前方案：同一批目标5人完成两个实验；各实验内原版/改进为被试内比较。可分两次完成，沿用同一匿名编号。扩展规则见05文档。
- 推荐理由：小样本时可以直接比较同一个人的变化，减少个体差异；代价是练习、疲劳和顺序影响，需平衡顺序、安排休息与独立刺激。
- 不把10人拆成每条件5人后仍声称“每条件10人”；不把做了两个实验的10人写成20名被试。

## 收数平台接入与项目数量

等两实验和关键改进确定后，用户在/hw2创建一个项目即可。一个项目容纳全部实验/版本，不需要每个版本各建项目，idea小幅调整也不自动要求新建项目。

平台接口支持两种组织方式：

1. **按范式上传（优先建议）**：`experiment=visual_search`包含原特征、原联合和改进联合试次；每条trial有`variant`等条件字段。比例判断同理用`graphical_judgment`。每人做完一个范式POST一次，即每人通常两次。平台能直接显示各范式人数；网页需自己核验每条件试次数。
2. **按版本上传（老师示例方式）**：如`search_feature`、`search_conjunction`、`search_grouped`分别上传；网页按同一匿名编号合并配对。更容易在平台逐版本看人数，但记录管理更多。

二者都使用老师支持的字段，不改接口。正式实现前选定一种并冻结，不能收数后随意换标识导致同一条件被拆成多个实验。

`condition`顶层字段留给被试间分组；被试内逐试次条件写入trials。收数成功才标记上传完成；失败保留备份并重试，避免重复提交。正式编号不含姓名学号，版本/会话ID用于数据核验而非身份识别。

## 报告的简单结构

1. 设计与预测：我们要复现什么、检验什么改动。
2. 实际样本与数据质量：多少人、多少试次、怎么处理缺失。
3. 实验一：原效应与改进比较，一组图配简洁文字。
4. 实验二：同样结构。
5. 原论文对照、共同结论与局限。

个人反馈页可以即时给本人描述；正式报告应采用固定的数据截止时间和分析样本，避免平台人数后来变化导致正文与图不一致。
